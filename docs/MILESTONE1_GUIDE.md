## Part A: Running the project

### A1. What you need

| Tool | Why | Install |
|---|---|---|
| Linux, macOS or WSL | The Makefile uses a Unix shell | — |
| `uv` | Creates the Python 3.11 environment and installs packages. It downloads Python 3.11 itself if needed | `curl -LsSf https://astral.sh/uv/install.sh \| sh` |

### A3. Quick start: run the API in 2 commands

```bash
cd VPN-Classifier-MLOps     # or the submission folder
make setup                   # creates .venv (Python 3.11) and installs pinned packages, ~2 min
make serve                   # starts the API on http://127.0.0.1:8000
```

Open **http://127.0.0.1:8000/docs** in a browser. This is the Swagger UI, generated by FastAPI. Click `POST /predict` → **Try it out**. A VPN example is pre-filled; click **Execute**.

From a second terminal:

```bash
curl http://127.0.0.1:8000/health
# {"status":"ok","model_loaded":true,"model":"hgb_slow","version":"20261019-173911"}

curl -X POST http://127.0.0.1:8000/predict -H "Content-Type: application/json" -d @examples/vpn_ip.json
# {"is_vpn_proxy":true,"probability":0.9923,"threshold":0.9015,...}

curl -X POST http://127.0.0.1:8000/predict -H "Content-Type: application/json" -d @examples/regular_ip.json
# {"is_vpn_proxy":false,"probability":0.0055,...}

curl -X POST "http://127.0.0.1:8000/explain?top_k=3" -H "Content-Type: application/json" -d @examples/vpn_ip.json
# contributions: has_shodan +0.394, headers_hash_shared +0.058, n_tcp_ports +0.054

# Validation in action: a negative count is rejected with 422 and a clear message
curl -X POST http://127.0.0.1:8000/predict -H "Content-Type: application/json" -d '{"n_signals": -1}'
```

Stop the server with `Ctrl+C`.

```bash
make data SAMPLE=1    # validates data/sample/, builds features, splits 240 train / 60 test IPs

```

With `SAMPLE=1`, everything goes to `data/processed-sample/` and `models/sample/`, so the real model in `models/model.joblib` is never touched. Its MLflow runs go to a separate experiment, `vpn-proxy-classification-sample`.

The sample has synthetic labels, so its scores mean nothing. It only shows that the pipeline runs. CI runs exactly this.

### A6. The whole pipeline on the real data

1. Download `train.parq` and `shodan_df_hashed.csv` from the CrowdSec Kaggle competition. Put both in `data/raw/`. A symlink works too: `ln -s /path/to/train.parq data/raw/train.parq`.
2. Run:
   ```bash
   make data     # ~2.5 min, ~6 GB RAM: 61.6M signals → 148,259 IPs → 118,607 train / 29,652 test
   make train    # ~11 min on 4 cores: 5 models × 5-fold CV, best one saved to models/
   ```
3. Expected output (the seeds are fixed, so you should get the same numbers):
   ```
   logreg      cv_f1=0.5936  test_f1=0.5968
   rf          cv_f1=0.7607  test_f1=0.7502
   rf_shallow  cv_f1=0.7291  test_f1=0.7085
   hgb         cv_f1=0.7661  test_f1=0.7608
   hgb_slow    cv_f1=0.7694  test_f1=0.7663
   Best: hgb_slow
   ```

If the machine has less RAM, lower DuckDB's memory cap: `DUCKDB_MEMORY_LIMIT=3GB make data`. DuckDB then spills to disk and runs slower.

## Part B: How it works (viva preparation)

### B1. The problem in one paragraph

CrowdSec is a crowdsourced security tool. Thousands of machines (called **watchers**) report attacks they see, and each report is a **signal**: time, attack type, the attacker's IP (anonymised), the attacker's country and autonomous system (AS, the network the IP belongs to), and the same for the watcher. Our task is **binary classification**: given an attacker IP's signals, predict whether that IP is a **VPN or proxy**. That matters because a VPN/proxy hides the real origin of an attack.

### B2. The data

- `train.parq`: **61,629,685 signals** from **148,259 attacker IPs**, July 30 – August 29, 2023. Columns: `attack_time`, `attack_type`, `attacker_ip_enum`, `attacker_as_num/name`, `attacker_country`, `watcher_uuid_enum`, `watcher_as_num/name`, `watcher_country`, `label`.
- `shodan_df_hashed.csv`: for each IP, what Shodan (an internet-wide scanner) saw on it: open ports (e.g. `443/tcp`) and hashed fingerprints of its TLS/HTTP software (**JARM**, **JA3S**, **HTTP header hash**).
- **Imbalance:** only **2,890 IPs (1.95%)** are VPN/proxy.
- Kaggle's `test.parq` has no labels, so we don't use it. Our test set is a held-out 20% of the labelled IPs.

### B3. The key design decision: one prediction per IP

The label belongs to the **IP**, but the data has one row per **signal**. An IP can have anywhere from 1 to 1.4 million signals (median 37). Two options were considered:

1. **Predict per signal.** Every row repeats its IP's label, so the model sees the same answer thousands of times, and a random split leaks IPs between train and test.
2. **Aggregate per IP** (our choice). Each IP becomes one row of behavioural features. This matches how the label is defined, and the 2nd-place Kaggle solution also predicts per IP.

**Viva answer:** "We aggregate per IP because the label is per IP. It also makes leakage impossible: with one row per IP, the same IP can't be in both train and test."

### B4. The 28 features (`src/features.py`)

| Group | Features | Intuition |
|---|---|---|
| Volume & timing | `n_signals`, `active_hours`, `n_active_days`, `signals_per_day`, `max_signals_per_hour`, `mean_gap_s`, `median_gap_s` | VPN users attack sparingly over many days. Bots spam in bursts |
| Breadth | `n_attack_types`, `n_watchers`, `n_watcher_as`, `n_watcher_countries`, `n_attacker_as` | How widely an IP is seen |
| Attack mix | `share_http_spam`, `share_http_scan`, `share_http_exploit`, `share_http_bruteforce`, `share_http_crawl`, `share_ssh_bruteforce`, `share_pop3_imap_bruteforce`, `share_tcp_scan` | Fraction of the IP's signals of each type: the 8 types seen from over ~2,000 IPs |
| ASN crowding | `asn_unique_ips` | How many attacker IPs share this IP's network |
| Shodan | `has_shodan`, `n_tcp_ports`, `n_udp_ports`, `jarm_shared`, `ja3s_shared`, `headers_hash_shared`, `no_print_with_ports` | VPN servers run the same software, so **many IPs share the same fingerprint** |

**What the data shows** (median, VPN vs not): active days 9 vs 3; signals per day 6 vs 12; headers_hash_shared **690 vs 0**; has_shodan 1 vs 0.

**Never a feature:** `attacker_ip_enum`, the IP's ID. Using it would let the model memorise IPs instead of learning behaviour. It is used only to group signals.

**Why DuckDB?** 61.6M rows don't fit comfortably in pandas memory: the Kaggle notebook needed 6 GB or more just for its intermediate frames. DuckDB is an in-process SQL engine that streams the Parquet file and spills to disk if needed. The whole aggregation is one SQL query, using `GROUP BY` per IP, a `lag()` window for gaps, and joins for ASN size.

**Timezone:** `attack_time` is stored with a time zone. The DuckDB connection is pinned to UTC, so day and hour buckets don't change with the machine's time zone.

### B5. Data validation (`src/prepare_data.py`)

Before any features are built, `validate_signals` checks:

- required columns exist
- the ID, time, type and label columns have no nulls
- labels are only 0 or 1
- **every IP has a single label**
- the time range is valid

After building, `validate_features` checks that there is one row per IP, no NaNs and no negative values. Any failure raises `DataValidationError` with a clear message. **Real issue found:** `watcher_country` is null in 349K rows, so `n_watcher_countries` can be 0, and the API allows that.

### B6. Split and leakage

- **Stratified 80/20 split** of the per-IP table: 118,607 train / 29,652 test. Both sets keep the ~2% positive rate.
- `split_by_ip` **asserts** that no IP appears in both sets.
- **Model selection uses only the training set**, via 5-fold cross-validation. The test set is scored once per model, purely for reporting. If we picked the model with the best *test* score, the test score would no longer be an honest estimate.

### B7. Class imbalance and the threshold

- **Why not accuracy?** 98% of IPs are not VPN, so a model that always says "not VPN" scores 98% accuracy and is useless. Even our worst model has 98.4% accuracy.
- **Metric: F1 of the VPN class**, the harmonic mean of precision (of the flagged IPs, how many are really VPN) and recall (of the real VPNs, how many we catch).
- **Class weights:** all models use `class_weight="balanced"`, so mistakes on the rare class cost more.
- **Threshold tuning:** a model outputs a probability, and the default cut-off of 0.5 is arbitrary. For each model, we take the cross-validation out-of-fold probabilities, sweep all thresholds with `precision_recall_curve`, and keep the one with the highest F1. `hgb_slow`'s threshold is **0.90**. Balanced class weights push probabilities up, so a high cut-off is expected. The threshold is saved with the model and used by the API.

### B8. Models and results (`src/train.py`)

| Run | What it is | CV F1 | Test F1 |
|---|---|---|---|
| `logreg` | Logistic regression on log1p-transformed, standardised features | 0.594 | 0.597 |
| `rf` | Random forest, 200 trees | 0.761 | 0.750 |
| `rf_shallow` | Random forest, 300 trees, max depth 12 | 0.729 | 0.709 |
| `hgb` | HistGradientBoosting, learning rate 0.1, 300 iterations | 0.766 | 0.761 |
| **`hgb_slow`** | HistGradientBoosting, lr 0.05, 600 iterations, 63 leaves, L2 1.0 | **0.769** | **0.766** |
| `ludwig_automl` | Ludwig neural net, best of 20 AutoML trials | 0.723 (val) | 0.711 |

**Why `hgb_slow` won:** it has the highest CV F1, and that is the rule we fixed in advance. Its test F1 is also the best, which confirms the choice wasn't luck. It reaches precision 0.733, recall 0.803 and PR-AUC 0.797, and the model file is 294 KB.

**Why logistic regression is weak:** it can only add up feature effects. The real pattern is an interaction: "in Shodan **and** shares fingerprints **and** attacks slowly". Trees capture interactions naturally.

**HistGradientBoosting in one sentence:** it builds trees one after another, each correcting the errors of the previous ones, on binned feature values ("histogram"), which makes it fast on 100K+ rows.

### B9. The model bundle (`src/model_io.py`)

`models/model.joblib` is a dictionary, not just the model:
- `model`: the fitted estimator
- `features`: the exact feature order it expects
- `threshold`: the tuned cut-off
- `reference`: training medians for each feature, used by `/explain`
- `metadata`: name, version, MLflow run ID, metrics

`load_bundle` refuses a missing file, a corrupt file, a dict with missing keys, a model without `predict_proba`, or a threshold outside (0, 1). That is why `/health` can report `degraded` instead of the API crashing.

**Versioning:** each training run saves `models/vpn-clf_<model>_<UTC timestamp>.joblib` and copies the best one to `models/model.joblib`, which is what the API loads. `model_meta.json` records which version it is and its MLflow run ID.

### B10. The API (`src/app.py`)

- **FastAPI** generates `/docs` (Swagger) and `/openapi.json` automatically from the type hints.
- **Pydantic** `IPFeatures` validates every request:
  - All 28 fields are required, and unknown fields are rejected (`extra="forbid"`).
  - Counts must be ≥ 0, or ≥ 1 where every IP has at least one: `n_signals`, `n_attack_types`, `n_watchers`, `n_active_days`, `max_signals_per_hour`.
  - Shares and flags must be in [0, 1].
  - Invalid input gets **422** with the exact field and reason.
- **Startup:** the model is loaded once, in the `lifespan` hook, not on every request.
- **`/predict`:** returns the probability, `is_vpn_proxy = probability ≥ threshold`, and the model version.
- **`/explain`**, which is model-agnostic: for each feature, replace it with its training median, re-predict, and report `effect = original probability − new probability`. A positive effect means that feature's value pushes the IP towards VPN. This takes 28 extra predictions, which is milliseconds. It works for any model, unlike tree-specific importances, and it answers "why *this* IP?", not just "which features matter overall?".
- **Example:** for the VPN example, `has_shodan=1` adds +0.39 and `headers_hash_shared=690` adds +0.06.

### B11. MLflow (experiment tracking)

Each candidate is one **run** in experiment `vpn-proxy-classification`, with:
- **params:** model type, folds, training size and all hyperparameters (18–25 per run)
- **metrics:** `cv_f1`, `cv_pr_auc`, `threshold`, `test_f1`, `test_precision`, `test_recall`, `test_pr_auc`, `test_roc_auc`, `test_accuracy`
- **tags:** the best run gets `best_model=true`. The Ludwig run gets `automl=ludwig` and also stores its best config and all 20 trial scores as artifacts.

The tracking backend is a local SQLite file, `mlflow.db`, or DagsHub when `MLFLOW_TRACKING_URI` points there. The code is the same either way.

### B12. Ludwig AutoML (`configs/ludwig_automl.yaml`, `src/automl_ludwig.py`)

- **Ludwig** is a declarative deep-learning framework: you describe inputs, outputs and training in YAML instead of writing PyTorch.
- **Our config:**
  - **Inputs:** the 28 features (always-≥1 counts get `log1p`, the others `zscore`, and flags are binary).
  - **Output:** `label` (binary, weighted cross-entropy).
  - **Model:** a concat combiner (dense layers).
  - **Search:** a `hyperopt` section. It searches learning rate, batch size, number of layers, layer width, dropout and positive-class weight, using **Ray Tune** with the **TPE** algorithm and **ASHA** early stopping, for 20 trials with a 1-hour cap.
- **The runner:**
  - splits the training IPs into train and validation (the test set is untouched)
  - runs the search, scoring each trial on validation ROC-AUC
  - retrains the best trial and tunes its F1 threshold on validation
  - scores it on the same test set as the sklearn models and logs it to MLflow
- **Result:** test F1 0.711, behind the gradient-boosted trees. On tabular data, tree ensembles usually beat neural nets, and they are smaller and faster to serve.
- **Practical issues we solved, which make good viva answers:**
  1. **Python version:** Ludwig ≥ 0.11.1 needs Python 3.12, and the course requires 3.11, so we pinned 0.11.0.
  2. **Normalization:** Ludwig's `log1p` rejects zeros, so zero-capable counts use `zscore`.
  3. **Constant columns:** Ludwig refuses to z-score a constant column, so the runner drops those.
  4. **Missing dependency:** the Ray executor needs `dask`, which the `[hyperopt]` extra doesn't install.
  5. **Crash bug:** Ludwig 0.11 crashes when re-evaluating ASHA-stopped trials, because their checkpoint has no saved weights. We skip that step, because we retrain the best trial ourselves.

### B15. Design trade-offs (for the 1–2 minute discussion)

Pick one for the presentation:

1. **Per-IP aggregation vs per-signal:** matches the label, removes leakage, and is 400× fewer rows. The cost is that the API takes aggregated features, not raw signals.
2. **HistGradientBoosting vs Ludwig neural net:** the trees won by 5.5 F1 points, train in minutes on a CPU, and give a 294 KB model. AutoML is not automatically better.
3. **F1 + tuned threshold vs accuracy:** at 2% positives accuracy is meaningless, and tuning the threshold mattered more than the model's default 0.5.
4. **DuckDB vs pandas:** handles 61.6M rows in 2.5 minutes with a capped memory budget on a laptop.

### B16. Likely viva questions with short answers

- **Why is the threshold 0.90 and not 0.5?** Balanced class weights inflate positive probabilities. We pick the threshold that maximises F1 on cross-validation predictions, not on the test set.
- **How do you prevent data leakage?** One row per IP, a stratified split with an assertion of no IP overlap, and model and threshold selection on CV only. The IP ID is not a feature.
- **What happens if someone sends bad input?** Pydantic returns 422 with the field and the reason. Unknown fields are rejected too.
- **What if the model file is missing?** `/health` reports `degraded` with the reason, and `/predict` returns 503. The API doesn't crash.
- **How does /explain work?** It replaces one feature at a time with its training median and measures the change in probability. It is model-agnostic.
- **What is PR-AUC and why report it?** The area under the precision-recall curve. It measures ranking quality on the rare class, independent of the threshold, and is more informative than ROC-AUC under heavy imbalance: ROC-AUC is 0.97–0.99 for every model.
- **Where did the feature ideas come from?** They were adapted from the public 2nd-place Kaggle notebook and credited in the README. Our code is a reimplementation, in DuckDB instead of pandas.
- **How would you add a new model?** Add one entry to `CANDIDATES` in `src/train.py`. It is automatically cross-validated, logged to MLflow and considered for selection.
- **What does `asn_unique_ips` capture?** How crowded the IP's network is. Hosting and VPN networks host many attacker IPs.
- **Why is the Ludwig environment separate?** Ludwig brings PyTorch and Ray (~2 GB) and its own version pins. The API and CI don't need it.
