Using the attached project brief, create a PowerPoint presentation of about 16 slides for our MLOps course. The audience is our instructor and classmates, who know machine learning basics but not this project. Follow the brief's slide outline and use its figures.

Rules:
- Use only the numbers in the brief. Don't round them differently or add new results.
- Always say which model a number belongs to. The deployed model (hgb_slow, test F1 0.7663) and the best experimental model (400 trees, test F1 0.7876) are different, and the experimental model isn't deployed.
- Label cross-validation, validation and test scores. Models were selected on cross-validation or validation scores, never on test scores.
- Describe Ludwig as hyperparameter search on a fixed neural network, not full AutoML. Don't say Ludwig or neural networks are worse in general.
- Describe SHAP as explaining the model's behaviour, not as showing what causes an IP to be a VPN or proxy.
- Check the Status section. Anything marked in progress or not done must be presented that way, never as finished.
- Each slide title should state its main finding. Keep slides light, and put details in the speaker notes.

The project predicts whether an attacker IP seen by CrowdSec is a VPN or proxy. It covers the full MLOps path: data validation, feature engineering, experiment tracking, model comparison, explainability, a FastAPI service, a Streamlit dashboard and automated tests.

Problem and data

  • Task: binary classification, one prediction per attacker IP.
  • Source: CrowdSec community data from a Kaggle competition. train.parq has 61,629,685 attack signals from 148,259 IPs (30 July to 29 August 2023). shodan_df_hashed.csv has open ports and hashed fingerprints.
  • Main metric: F1 of the VPN/proxy class. Labelling every IP "not VPN" scores 98.05% accuracy but F1 of 0, so accuracy is misleading.
  • Split: stratified 80/20 by IP: 118,607 train, 29,652 test. One row per IP means no IP appears in both. Kaggle's own test file has no labels, so our test set is a held-out share of labelled IPs.

Pipeline

1. Preparesrc/prepare_data.py validates the raw data, then DuckDB builds one row per IP
2. Trainsrc/train.py compares 5 models with 5-fold CV and tunes an F1 threshold
3. Experimentexperiments/ runs A to F on the same split and folds
4. TrackMLflow records parameters, metrics and artifacts, in SQLite or on DagsHub
5. ServeFastAPI loads models/model.joblib at startup
6. UseThe Streamlit dashboard reaches the model only over HTTP

MLflow records results, but it doesn't choose or serve models. The API loads a file from disk. Only experiments/promote_model.py, with explicit approval, or a new src/train.py run changes that file.

What the experiments found

ExperimentQuestionFinding
BaselineDoes the original result reproduce?Yes: all 5 models match the documented scores to 4 decimal places.
A: thresholdDoes tuning the threshold matter?hgb_slow at the default 0.5 has test F1 0.6041 (precision 0.453, recall 0.908). At the tuned threshold 0.9015 it has 0.7663.
B: imbalanceDoes resampling help?Oversampling 1:1 reached test F1 0.7813 and no class weights 0.7772. Undersampling 1:1 fell to 0.7229. Neither was selected overall.
C: hyperparametersWhich settings matter?Biggest finding: hgb_slow was documented as 600 trees but built only 94, because scikit-learn's early stopping turned on automatically. Turning it off with 400 trees gave the selected model.
D: featuresHow much does it rely on Shodan?Heavily. Without the 7 Shodan features, test F1 falls to 0.5923. Only the Shodan features gives 0.7451.
E: model familiesWhich family wins?hgb_slow by CV F1, though its win over hgb is within fold-to-fold noise of about ±0.02.
F: LudwigDoes automated search on a neural network beat trees?Not in this run: test F1 0.7020. See the Ludwig section.

Selection rule: highest 5-fold CV F1, must beat the baseline by at least 0.003, and the simplest option within 0.003 of the best wins. The highest test F1 of any run, 0.7935, wasn't chosen, because choosing it would be selecting on the test set. About 50 configurations were scored on test, so only the selected model's test score is a fair estimate.

Population-count features (leakage check): asn_unique_ips, jarm_shared, ja3s_shared and headers_hash_shared count across the whole raw files before the split, including test IPs and 49,420 unlabelled Kaggle test IPs. They never read a label, so no label information leaks, but the design is transductive. Counted over training IPs only, using one frozen table, test F1 moves from 0.7663 to 0.7608, with a difference interval of −0.019 to +0.007. Existing results weren't regenerated. An alternative table can be written with a flag.

A real risk: an offset of one between how training and new rows were counted cost about 0.06 F1. These counts must be computed identically in training and serving.

Explainability

MethodScopeQuestion it answersWhere
Permutation importanceGlobalHow much does test F1 drop if this feature is shuffled?src/explain.py
Median replacementLocalHow does the score change if this one feature becomes typical?POST /explain
SHAP summary and bar plotsGlobalHow much does each feature move the score, on average?src/shap_report.py
SHAP local valuesLocalWhich features pushed this score toward or away from VPN/proxy?POST /explain/shap, dashboard
  • Explainer used: shap.TreeExplainer, tree-path-dependent, on shap 0.54.1 and scikit-learn 1.9.1. It works directly on HistGradientBoosting, so no fallback was needed. Non-tree models fall back to PermutationExplainer, and the response names the one that ran.
  • Correctness: values are in log-odds of the VPN/proxy class. Every call checks that the base value plus the SHAP values equals the model's own log-odds. Measured error on real data was about 1e-14.
  • Top SHAP features, hgb_slow, all 29,652 test IPs: has_shodan (0.734), n_tcp_ports (0.362), signals_per_day (0.285), asn_unique_ips (0.151), share_http_scan (0.148), headers_hash_shared (0.122).
  • Top permutation features, same model: has_shodan (F1 drop 0.445), n_tcp_ports (0.348), headers_hash_shared (0.247), asn_unique_ips (0.110), share_http_scan (0.039).
  • Agreement: the two rankings have a Spearman correlation of 0.83. They differ because one measures movement in the score and the other measures dependence for F1.
  • Limit: all of these describe the model's behaviour. None shows that a feature causes an IP to be a VPN or proxy.

Ludwig hyperparameter search

We fix one ECD (encoder-combiner-decoder) neural network, and Ludwig tunes its settings: learning rate, batch size, layers, width, dropout and positive-class weight. It doesn't compare model families or choose features, so this is hyperparameter optimisation rather than full AutoML.

  • The TPE discovery: the config names TPE, but its default of 20 random startup points used up all 20 trials. Inspecting the real searcher object confirmed n_startup_jobs = 20.
  • A second, hidden problem: Ludwig 0.11 silently drops n_initial_points when it loads a config, so setting it in YAML does nothing. The script now applies it to the searcher directly, stops if that fails, and counts which suggestions really were random or adaptive. A 4-trial check on the real pipeline, set to 2 startup points, measured 2 random and 2 adaptive suggestions.
  • Why PR-AUC: across 72 runs on the same folds, using CV results only, PR-AUC tracks F1 far better than ROC-AUC (Spearman 0.926 vs 0.631). Those are tree models, so it's evidence about the metrics on this data. Ludwig has no binary PR-AUC, so we added one, and it matches scikit-learn's value on a test sample (0.85766).
  • Test safety: the test set isn't given to the search, and the threshold is tuned on validation only. Validation also picks the best epoch, so that threshold is slightly optimistic.

  • Manual form kept: the dashboard still has all 28 inputs, now with meaning, unit and kind on each field, plus reset, loading a real record by ID, random records by split and label, and pasting a row from Excel.
  • The model doesn't read IP addresses. It scores engineered features, and there's no automatic Shodan lookup, so an arbitrary IP can't be classified from its address alone.
  • Excel export: python -m src.export_features writes all 148,259 IPs to data/exports/ip_level_aggregated_features.xlsx (23 MB), with an Instructions sheet, a Feature_guide sheet, a frozen header and filters, plus a 60-row sample covering every outcome. Values are read from the training tables, so nothing is recalculated.
  • Safe deployment: experiments/promote_model.py changes nothing without --approve and a reason. It refuses a lower CV F1 whatever the test score, archives the old model and logs the decision.
  • Speed: on the live API, /predict took about 80 ms and /explain/shap about 75 to 560 ms, on a laptop with other jobs running.

  • Lint: Ruff passes across src, tests, ui and experiments.
  • Live check: real records of all four outcomes (true positive, false alarm, missed, true negative) gave the same score through the running API as the model directly.

Limitations to state honestly

  • The label's origin is unknown. If labels were built using Shodan, its predictive power could be partly circular, so this should be asked of the data provider.
  • The Shodan file has no timestamps, so we can't confirm it predates the attacks.
  • New IPs need their signals aggregated and Shodan data supplied. The project has no live lookup.
  • Population counts must be computed identically in serving, and the API can't check how they were produced.
  • The best model isn't deployed yet, and the 400-tree gain has a low end close to zero.
  • Scores use class weights, so read them against the threshold rather than as literal probabilities.
  • The final selection rule was written after seeing CV results, though before any new test scoring.

Likely viva questions

QuestionShort answer
Why not use accuracy?Only 1.95% of IPs are positive, so predicting "not VPN" for everything scores 98.05% with F1 of 0.
Why isn't the best model deployed?Deployment needs an explicit decision. It's packaged and passes the promotion checks, but the team hasn't approved it.
Why not pick the run with test F1 0.7935?That would be selecting on the test set, which makes its score optimistic.
Is your project full AutoML?No. It's automated hyperparameter search on a fixed network. We chose the features, normalisation and model family.
Was the first search Bayesian?It was configured for TPE, but all 20 trials were random startup trials, so in practice it was random search.
Does MLflow deploy your model?No. FastAPI loads models/model.joblib. MLflow records results, and the run ID links the two.
Is there data leakage?No IP overlaps the split, and no feature reads a label. Four population counts include test IPs, which is transductive. Counting only training IPs changed test F1 by an amount not clearly different from zero.
Does a high SHAP value mean a feature causes VPN use?No. It means this model relied on that feature for this score.
Can I enter any IP address?No. The model needs 28 engineered features, which require CrowdSec signals and Shodan data.
